Grant Radar

Funding intelligence for nature, biodiversity, ecology, environment, climate, water, and energy.

How it works

Grant Radar is a static funding-intelligence console backed by generated JSON data, scheduled GitHub Actions, curated source registries, and a separate review layer for newly discovered candidate pages.

01

Source registry

  • Trusted funding sources are defined in source-registry.json.
  • Each source carries purpose tags, applicant fit, access route, scale, status hints, and mode relevance.
  • Current packs include water quality, NbS, climate enterprise, farmer routes, research routes, and Geo / Earth Systems.
02

Discovery layer

  • discover_grants.py scans selected seed pages for new funding-like links.
  • Generic pages, stale pages, parent pages, and already-covered sources are suppressed where possible.
  • Potentially useful links go to discovery-candidates.json, not directly to the public catalogue.
03

Review gate

  • The review page is an inspection layer for candidate IDs, source URLs, confidence, and suppression reasons.
  • Promotion and rejection happen through the admin workflow, not by automatic publication.
  • This keeps the public catalogue curated while still allowing the radar to discover new material.
04

Harvest pipeline

  • harvest_grants.py builds the trusted public catalogue from approved registry sources.
  • It refreshes deadlines, programme state, visibility state, source metadata, and change flags.
  • Fallback logic protects the public catalogue when official websites block or fail requests.
05

Generated JSON front end

  • The site reads catalog.json directly in the browser.
  • No database, server, login system, or paid API is required for the public site.
  • GitHub Pages serves the interface as a fast static application.
06

Mode-first filtering

  • Users start with curated modes: River Trust, Farming & water quality, Climate Entrepreneur, Research, or Geo / Earth Systems.
  • Advanced purpose filters remain available, but they no longer dominate the interface.
  • Mode relevance is encoded in the data layer, so the UI is not just a cosmetic mask.
07

Audit trail

  • discovery-audit.json records seed coverage, candidate counts, suppressions, and fetch failures.
  • harvest-audit.json records catalogue build state and source health.
  • source-memory.json and harvest-memory.json support change detection across runs.
08

Automation boundary

  • Scheduled GitHub Actions refresh discovery, harvest the catalogue, run health checks, and commit generated data.
  • The public site remains deterministic: no live scraping from the browser and no paid AI dependency.
  • Human review remains the quality boundary between discovery and publication.
